1. 多 worker 并发怎么控制
一个 worker = 一个 Mineflayer bot/runtime 连接，用来独立跑一个 task attempt。

总流程是：
    task_ids → 分成 task_waves → 每个 wave 建一个 asyncio.Queue → 把每个 task_id 包成 TrainingTaskRequest 放进队列 → 启动 N 个 worker_loop → 每个 worker_loop 从队列拿一个任务 → 跑 ExecutionLoop.run → 产出 outcome → 如果可重试再把 retry_request 放回队列。

worker_concurrency 控制同时有几个 worker 跑任务：最多 worker_concurrency 个 worker 同时跑；任务少于 worker 数时，只开任务数量那么多 worker。


task_waves 是波次控制：没有配置 waves 时，所有 task_ids 在一个 wave 里，由 worker 池并发跑。配置了 waves 时，先跑第 1 波，全部完成后再跑第 2 波。

为什么要 wave？
    有些任务/实验需要分阶段跑，或者想控制同一批任务共享同一个 skill snapshot

worker_concurrency：同时跑几个 Minecraft worker / task attempt。
model_concurrency 控制：同时有几个大模型请求在飞。
max_task_retries：普通任务失败最多重试几次。
model_timeout_requeues：模型超时导致的重入队次数。
worker_failure_requeues：worker 失联/action_rpc_timeout 后的恢复重试次数。
task_retry_delay_sec / model_timeout_requeue_delay_sec：重试前等待。

skill snapshot：（skill snapshot 是训练批次开始时冻结下来的 promoted skills 列表。因为多 worker 并发时，如果 worker A 刚跑完生成了新 skill，worker B 立刻看到它，会导致同一个 batch 内不同 worker 看到的 skill 库不一致。）
    batch 开始 → capture_snapshot() → 所有 worker 都用这份固定 skill snapshot → batch 结束后再统一处理 skill 更新。

并发训练不是让多个 worker 共享实时变化的技能库，而是在 batch 开始时冻结 promoted skills 和 active learning candidates，所有 worker 在同一批任务中只读这份 snapshot；任务通过 waves 和 worker queue 并发调度，LLM 请求再由 semaphore 单独限流；batch 完成后系统统一根据轨迹和 verifier 结果进行失败分类、恢复验证、候选技能生成、重复检测和可选晋升，从而避免并发 worker 互相看到刚生成的经验导致训练状态不一致。MineCLIP 则是外部视觉文本评分模型，项目不训练它，只把它作为 creative task 的在线反馈和离线评估工具接入。


简历：
整体：
    这块本质不是“一个 hook 系统管所有事”，而是把任务运行拆成几个生命周期边界：任务开始前重置环境、每步 action 前后做拦截和记录、动作超时后做 worker 健康探测、批量任务失败后重试或恢复 worker、run 结束后写 trace 和触发 skill/learning 后处理、人工审核和 skill 晋升时用数据库事务保证一致性。

这块不是一个单独模块完成的，而是 ExecutionLoop 负责单步流程，LiveRunner 负责批量并发和重试，Recorder 负责审计记录，数据库事务负责 skill/learning 写入一致性。

1. 生命周期治理
生命周期治理指的是把一次 Agent 任务从启动、执行、异常恢复到结束后的审计和技能写入，都纳入统一的可控流程。核心不是单纯跑通任务，而是保证每个 run 都有明确身份、可追踪状态、失败恢复策略和持久化记录。

主循环按生命周期节点做治理，action 前后提供 hook 扩展点。

任务启动治理： ExecutionLoop 会初始化 run、reset runtime，并记录 run_started / environment_reset 等事件；live runner 会给每个 task attempt 标记 task_id、run_id、worker_id 和 attempt，保证并行训练时每个任务都有独立身份和审计边界。

执行过程治理： 模型输出 action 后，会先经过结构化解析、ToolRegistry / Pydantic 校验，再进入 before_action；真正执行后进入 after_action，并统一记录 action_result。Hook 的作用是在模型决策和真实环境执行之间插入治理逻辑，比如安全门控、动作改写、结果审计和异常扩展。

异常治理： MineflayerClient 会给不同 action 配置 timeout；RPC 超时后再用 observe 做短健康探测，区分 worker 慢响应和 worker 失联。live runner 会根据失败类型决定是否 requeue 或 worker recovery，例如模型超时、worker 不响应可以重试，普通 gameplay 失败则更多进入失败分类和学习流程。

恢复治理： ExecutionLoop 支持 checkpoint / resume，把下一步 step、任务记忆和 run context 保存下来；恢复时会从 checkpoint 继续，并结合批次快照校验，避免任务恢复时读到不一致的技能状态。

审计治理： 会把 run、observation、context、model call、action_result、runtime_error、checkpoint 和 skill event 等写入数据库，让每一步都有证据链；creative 或需要人工判断的任务会进入 human_reviews，由 Dashboard 写入审核结果。

技能写入治理： 任务结束后，成功 run 进入 Skill candidate、去重和 promotion 流程，失败 run 进入 Learning Candidate 记录和恢复验证流程；写入侧通过 source_run_id、signature、唯一约束、事务和行级锁保证并行训练和任务恢复时状态一致。
一句话： Hook 只是 action 前后的插拔点；生命周期治理是围绕任务身份、执行安全、异常恢复、审计记录和技能写入一致性做的一整套控制机制。


2. Skill 写入怎么保证不乱
结构：
    概念上，一个 Skill 可以分成四块。第一块是身份信息，比如 name 和 version，用来标识技能版本，并作为数据库唯一键；真正防止语义重复时，还会比较动作类型、目标和触发词等相似度(0.82)。
    第二块是status用于启用/禁用/待审核只有 promoted 状态会进入后续上下文召回。
    第三块是召回信息，包含任务类型、目标 ID、触发词和所需动作，用于和当前任务做相关性匹配。
    第四块是使用与审计信息：strategy_summary、parameterized_plan 和 recovery_policy 会被压缩注入上下文
    第五块provenance为该skill对应的run的信息，用于人工审计和来源追踪：source_run_id、source_step_range、source_evidence、verifier_stats、validation 和 metrics 用来追踪这个技能来自哪次 run、效果如何、是否可信。

source_run_id 幂等：同一个成功 run 生成 skill candidate 时，会先查这个 run 有没有已经生成过 skill；有就复用，避免断点恢复或重复跑时生成两份。

Signature 是 Learning Candidate 的归一化失败模式唯一键，由任务范围、失败动作类型和失败状态组成，用于把并行训练中重复出现的同类失败聚合到同一条候选记录。
【source_run_id 是成功 run 到 Skill 的来源幂等键，防止同一次成功运行重复生成 Skill；signature 是失败模式的归一化键，用来聚合同类 Learning Candidate。】
Learning Candidate signature 去重：失败经验用稳定签名，比如“任务 scope + action 类型 + 失败原因”，数据库里 signature 唯一；同类失败会合并证据，不会无限新增。
harvest_oak_log + move_to + no_path

with_for_update 行级锁：在 Learning Candidate 更新、Skill 审核/晋升/废弃、人工审核等需要修改共享状态的场景，会通过事务和行级锁保护关键记录，避免并发覆盖。
Skill promotion：候选 skill 不是直接进模型上下文，只有状态变成 promoted 后才会被 Context Manager 召回。

3.  Hook 到底有什么用
Hook 的价值是“在不改主循环的情况下插入治理逻辑”。比如 before_action 可以在危险动作前做安全检查、暂停威胁状态、改写或拒绝 action；after_action 可以记录结果、触发监控或做清理。显式 LifecycleHooks 主要围绕 action 前后；其他节点是独立模块实现的。

observe -> build context -> LLM 输出 ActionDecision -> Pydantic 解析 -> ToolRegistry 检查 action 是否允许 -> before_action -> dispatch 执行 -> after_action -> recorder 记录 action_result -> success_checker/verifier 判断是否完成

4. 环境隔离
任务运行隔离 + 批次快照隔离 + 状态写入隔离

    1. 任务运行环境隔离
    每个任务启动前做 Minecraft reset / inventory reset ，避免上一个任务的世界状态、背包状态、worker 状态污染下一个任务。

    2. Worker 执行隔离
    批量训练里每个 worker 执行自己的 task attempt，通过 worker_id、run_id、job_id 标记身份，失败可以 requeue 或 recovery，不会把某个 worker 的中间状态直接写进其他 worker 的上下文。

    3. 学习可见性隔离
    在批量训练时，我们不会让 worker 立即读取其他 worker 刚生成的经验，而是在批次开始冻结一份 Skill/Learning 快照，所有 worker 在同一个批次里看到一致的上下文，批次结束后再统一写入学习结果。
