Execution Loop 可以理解为 Agent Runtime 的主控调度器。
普通 LLM 应用可能是：
用户输入 -> 模型回答 -> 结束
但 Minecraft Agent 不是这样。它面对的是一个会变化的真实环境，模型每一步都必须：
看环境 -> 思考 -> 选动作 -> 执行动作 -> 看结果 -> 判断任务是否完成 -> 继续
所以 Execution Loop 本质是一个 observe-think-act-verify-record 的闭环。


Execution Loop 设计成 Agent 的运行时控制平面。模型只负责在当前 observation 和 action scope 内做决策，Harness 负责环境重置、上下文构建、动作校验、执行调度、异常恢复、Verifier 判定、轨迹持久化和预算控制，从而把不稳定的 LLM 输出约束成可审计、可恢复的真实环境交互过程。

reset 环境 【在一次任务 Run 开始前，把 Minecraft 环境整理到这个任务需要的初始状态。按任务要求做环境初始化和隔离。
  -> observe 当前状态
  -> build prompt/context
  -> call model
  -> validate/repair action
  -> dispatch action
  -> record action result
  -> verify success
  -> save checkpoint
  -> next step

  在这个项目里，Execution Loop 是 Agent Runtime 的核心编排模块。我基于 ReAct 思路实现了 observe-action 的闭环，但没有让模型直接控制 Minecraft。每个任务首先从 task manifest 构造 task_spec，里面包含目标、reset plan、allowed actions、verifier 和预算。Run 开始后，Harness 重置环境，获取结构化 observation，再由 ContextManager 构建包含任务目标、状态摘要、历史压缩、记忆、知识和 Skill 的上下文。模型输出 ActionDecision，Harness 通过 Pydantic 和 ToolRegistry 校验 action 是否属于当前 action scope。如果模型输出非法动作，会进入 repair policy；修复失败则降级到低风险动作。合法 Runtime Action 通过 RPC 发给 Mineflayer worker 执行，Knowledge Action 则由 backend 内部处理。每一步都会记录 observation、model call、action result 和 verifier result，并定期保存 checkpoint。最终成功不由模型声明，而由 task verifier 基于环境证据判断。这个设计让 Agent 执行过程可控、可恢复、可审计，也为后续 Skill 学习提供了可靠轨迹数据。

完整 Execution Loop 用紧凑版写：
1. Harness 初始化 run：生成 run_id，整理 task_spec，确定 allowed_actions，准备 memory、run_context、previous_step。
2. Harness 可选加载 checkpoint：如果 resume，就恢复 next_step_index、task_memory、previous_step、run_context。
3. Runtime 重置环境：ExecutionLoop 调 runtime.reset(spec)，得到 reset_result，并记录 run_started。
4. Runtime 观察世界：每个 step 调 runtime.observe()，得到 observation，并记录 observation。
5. Harness 可选生成计划：如果有 planner 且还没有 task_plan，就让 planner 产出高层计划。
6. ContextManager 构建模型输入：把 task、observation、previous_step、run_context、allowed_actions 拼成 context.messages。
7. Recorder 记录上下文：把 context.audit_messages、prompt_sections、检索到的 skills/knowledge 等记到 context_built。
8. Model 输出决策：模型读取 context.messages，输出 ActionDecision，也就是 reasoning_summary、evidence、knowledge_need、memory_update、action。
9. Harness 校验/修复决策：ActionRepairPolicy 解析 JSON、校验 action，不合法就让模型重答，仍失败就 Harness 选择 fallback action。
10. Harness 执行 before_action hook：允许生命周期钩子在动作执行前检查或改写 action。
11. Harness 分流 action：知识 action 走 KnowledgeToolDispatcher，submit_for_evaluation 走 verifier，普通 runtime action 走 runtime.act。
12. Harness 可选 follow_handoff：如果 bot 正在 follow 且下一步要操作同一实体，就短暂轮询 observe 等它靠近。
13. Runtime/Knowledge/Verifier 返回 action_result：不同分支都统一产出 action_result。
14. Harness 应用 action_recommendations：如果 action 成功且配置了推荐下一步，就把 recommended_next_actions 写进 action_result。
15. Harness 执行 after_action hook：动作结束后给生命周期钩子一个处理机会。
16. Recorder 记录动作结果：记录 action_result 事件。
17. Harness 更新运行上下文：记录 memory source，应用模型请求的 memory_update，写入 trajectory，更新 steps 和 previous_step。
18. StateStore 可选保存 checkpoint：每隔固定步数保存 last_action、last_action_result、run_context 等断点信息。
19. Harness 判断是否结束：检查 timeout、terminated、submit_for_evaluation 是否被接受、success_checker 是否成功、max_steps 是否用完。
20. 如果没结束，下一轮用新的 previous_step/run_context 重新 build context；如果结束，记录 run_finished 并返回 ExecutionRunResult。



简历：
总框架
  单个任务：reset -> observe -> build context -> call model -> validate/repair action -> execute action -> record result -> verifier -> checkpoint/stop
  批量任务：task_ids -> waves -> worker queue -> worker 跑 ExecutionLoop -> 失败可 requeue -> wave 结束 -> batch 结束后统一做 learning/skill update

一、 React ,Planner-Execution 
1. 怎么用 or 协作？
Execution Loop 主体采用 ReAct observation-action 循环：每步先观察环境，构建上下文，让模型输出 ActionDecision，再由 Harness 校验、修复并执行 action，随后记录 action_result，并通过 Verifier 判断任务是否完成。系统还支持可选 Planner：Planner 生成的 TaskPlan 只作为上下文指导，在 no_path、empty scan、target lost 等情况下可触发有限次数的 plan revision，但最终仍是每步执行一个 HarnessAction。

2. Planner 失败怎么办？
3. planner 什么时候生成、什么时候改
如果 ExecutionLoop 配了 planner：第一次 observe 后、正式给执行模型 build context 前，planner 会根据任务和当前 observation 生成一个高层 task_plan。这个 plan 会放进 Context Manager 的 user message 里，给模型当“当前计划提示”。


plan 什么时候修改：某些动作结果明显打脸当前计划时，比如 move_to 返回 no_path / path_timeout / path_stopped，或者 scan 为空，planner 可以 revise plan；修订次数有上限，避免一直改计划。

3. 为什么 plan 不直接执行一串动作？
A：Minecraft 环境动态变化很大，直接执行宏容易过时；所以 plan 只给策略，实际每步仍基于最新 observation 决策。

二、 单任务 Execution Loop 怎么设计
【可靠性】
1. 模型侧恢复：
动作生成阶段有 timeout recovery，默认重试 2 次，backoff 是 2 秒和 5 秒；耗尽后该 run 标成 model_timeout，live training 默认允许重新入队一次。


2. 动作异常恢复
2.1 
  LLM 输出后先解析成 ActionDecision，再取里面的 action 给 ToolRegistry.validate 校验；如果 JSON 坏了、字段不对、action 不在本轮允许列表里，Harness 会把错误、坏输出、允许动作列表塞进 repair_request，让模型再生成一次；默认修复一次，仍失败就走安全 fallback。就降级到查背包或请求视觉快照这类低风险动作，
2.2 动作执行侧恢复
  Python 侧通过 RPC 发动作请求。每个动作都有超时保护，如果 worker 没按时返回，Harness 把动作状态标成 unknown，并额外发一次 observe 做健康探测：如果 observe 能返回，说明 worker 还活着；如果 observe 也失败，就认为 worker 可能卡死，需要恢复或重启。

修复：
  修复后的 ActionDecision（让模型自己重答一次：第一次坏输出 → Harness 指出错误，repair prompt 追加到原始 messages 后面 → 大模型重新输出修正版 ActionDecision || Harness 自己兜底：query_inventory or request_visual_snapshot,  "action": {"type": "query_inventory", "args": {}}

  Harness 兜底产出：比如 query_inventory

Action RPC timeout 和模型 timeout 区别是什么？
答：模型 timeout 是 LLM 没返回动作；Action RPC timeout 是动作已经发给 Mineflayer worker，但 worker 没在动作超时时间内返回结果，后者动作状态可能 unknown，所以要健康探测和 worker 恢复。

3. 步数和时间预算
预算分成步数预算和时间预算：步数控制模型最多决策几轮，超了结束状态通常会变成失败/未完成。时间预算控制单任务最多占用多久，超了结束状态通常会变成失败/未完成；live training 为了批量效率默认每任务 8 步，内部 step checkpoint 关闭，改由外层 wave checkpoint 保存批量进度。

4. Checkpoint断电冲泡：
5.1 ExecutionLoop 自己的 StateStore checkpoint 是单 run 断点，默认每 5 步一次，但 live training 里关掉了；
5.2 live training checkpoint 保存的是批量调度进度，而不是每一步动作；它记录完成了哪些 wave、已有任务尝试结果、原始 wave 计划，以及 skill/learning snapshot 版本。这样中断后可以跳过已完成 wave，并确保恢复时上下文和原批次一致。。

三、批量任务怎么跑
任务分成多个 wave，每个 wave 是一批可以同时跑的任务。进入一个 wave 后，系统会把任务请求放进异步队列，再启动多个 worker loop；每个 worker 空闲时就从队列拿一个任务，独立跑自己的 ExecutionLoop，跑完后记录结果，再继续拿下一个任务。

好处：
任务调度和 worker 不强绑定；失败任务如果满足重试条件，会被包装成新的 retry request 再放回队列；所以重试和普通任务走同一套调度机制。

恢复策略：
恢复策略按失败类型区分。普通任务失败默认不重试；模型超时可以重新入队一次；如果是 Action RPC 超时或 worker 无响应，系统会先调用 worker recovery，尝试重启或恢复 worker，恢复成功后才重新入队，避免在一个已经不可靠的 worker 上盲目继续跑。

checkpoint：
Checkpoint 也分两层：
单个 ExecutionLoop 本身支持按步保存断点，当执行中断或者api调用失败时或者动作，重新从数据库中加载上一轮的Action、Result、Memory、Run Context 和 Planner 状态，，然后重新observation(因为再次恢复时环境可能改变)。
批量训练：作用是：一批很多任务跑到第几个 wave，哪些任务已经完成，不要中断后从头重跑。
wave checkpoint； checkpoint JSON保存批量进度，比如哪些 wave 已完成、已有任务尝试结果、原始分批计划，以及当时使用的 skill/learning 快照版本。批量跑任务时，已经完整完成的批次不用重跑。。


1. waves：
waves：脚本根据 --worker-concurrency 和任务相似度规划 wave；默认 worker_concurrency=2，如果 --no-diverse-waves 或 worker 数 <= 1，就所有任务放一个 wave；否则 DiverseWavePlanner 会尽量把相似度低的任务放在同一批，默认相似度阈值 --max-task-similarity=0.45。

2. worker queue：
每个 wave 创建一个 asyncio.Queue，把 task_id 包成 TrainingTaskRequest 放进去，然后启动 N 个 _worker_loop；每个 worker 从 queue 拿任务，ExecutionLoop.run，跑完记录 outcome。

asyncio.Queue 做任务分发，worker loop 持续从队列取 TrainingTaskRequest；任务完成后调用 task_done，失败可重试时把新的 retry_request 再 put 回队列。”

3. 任务重试：
默认普通失败 max_task_retries=0，也就是不重试；模型超时默认 model_timeout_requeues=1；worker/RPC 类未知状态默认 worker_failure_requeues=1

4. Worker 恢复：
如果 failure class 是 action_rpc_timeout 或 worker_unresponsive，runner 会先调用 worker_recovery_callback，恢复成功才把 retry_request 放回 queue；恢复失败就不盲目重跑。

5. Checkpoint：
5.1 ExecutionLoop 自己的 StateStore checkpoint 是单 run 断点，默认每 5 步一次，但 live training 里关掉了；
  【单 run checkpoint 主要保存：
  next_step_index：下次从第几步继续
  task_memory：任务内记忆
  run_context：压缩轨迹、知识/技能 ledger 等上下文记忆
  task_plan：当前计划，如果有 planner
  last_action：上一轮动作
  last_action_result：上一轮动作结果】
5.2 live training checkpoint 保存的是批量调度进度，而不是每一步动作；它记录完成了哪些 wave、已有任务尝试结果、原始 wave 计划，以及 skill/learning snapshot 版本。这样中断后可以跳过已完成 wave，并确保恢复时上下文和原批次一致。。

四、Verifier
1. Verifier
Verifier 是任务成功条件的程序化检查器，不是让大模型自己判断成功。每个任务清单里会写成功条件，比如背包里是否有目标物品、是否放置了指定方块、是否击败了指定实体。执行循环每一步都会把当前轨迹状态交给 Verifier，它根据最新 observation 和 action_result 做确定性判断，返回 success、reason 和 checks。比如采集 dirt 的任务，Verifier 会看最新背包里 dirt 数量是否达到要求；如果达到了，就可以提前结束任务，不必等模型自己提交。

1.1 . Verifier 和人工审核分别负责什么？
常见检查包括背包物品数量、方块是否放置、实体是否击败、物品使用次数变化和存活时间；creative 类任务普通规则不好判断，所以会交给 MineCLIP 或人工审核。

2. 失败分类到底怎么做
如果 run 失败，Harness 会读取已经持久化的每一步 action_result，从里面找最后一个可复用的游戏层失败原因，比如 no_path、path_timeout、missing_ingredient、missing_station、target_unreachable。只有这种稳定的游戏失败会生成 Learning Candidate；像模型超时、运行时异常、验证不确定这类基础设施问题，默认不会沉淀成技能经验。

比如任务失败是因为 move_to 多次返回 no_path，系统会把它分类成导航类失败，并生成一条经验假设：遇到这个目标不可达时，不要反复 move_to 同一坐标，应该重新扫描或换目标。后续如果同 scope 的成功 run 解决了这个问题，这条失败经验才会被验证。





五、Skill 自进化怎么设计
Harness 通过 recorder 保存轨迹，再用任务结果和动作结果做失败分类、恢复验证和 skill candidate 生成。

1. 数据：
每个 run 会进 recorder，保存 observation、context、model_action、action_result、verifier_result、runtime_error 等；这些是后处理的证据。

2. 失败分类：failure candidate
失败 run 会进入 record_failure(run_id)，系统从持久化 run、step、action_result 里找可学习的失败，比如导航 no_path、path_timeout、timeout_no_progress

3. 恢复经验验证
后续如果某个成功 run 命中过之前的 failure candidate，record_success(run_id) 会把它记成 recovery evidence，也就是“这个失败模式后来被某条成功轨迹解决过”。

4. Skill Candidate 生成：
Skill Candidate 是从成功任务轨迹里提炼出来的“可复用操作流程”。任务成功后，Harness 会读取这个 run 的完整轨迹，比如观察、动作序列、action_result 和 verifier 结果，再判断这条成功路径是否值得沉淀成技能候选。候选里会记录它来自哪个 run，也就是 source_run_id，还会保存动作计划、适用场景、前置条件、证据，以及它是否解决过某些历史失败经验。


5. 并发一致性：
并发训练时，多个 worker 会同时跑任务。为了避免 worker A 刚生成的新经验立刻影响 worker B，系统在 batch 开始前会先冻结一份当前可用经验快照，包括已经正式晋升的 promoted skills 和当前 active learning candidates。本 batch 内所有 worker 都只读取这份快照；等整个 batch 跑完后，Harness 才统一根据结果记录失败经验、验证恢复经验、生成新的 Skill Candidate，必要时再晋升技能。这样可以保证同一批任务看到的上下文一致。


6. 什么条件/ Skill Candidate 为什么不是成功就生成？
满足创建条件时生成 Skill Candidate：
Skill Candidate 不是成功就必建。系统会先过滤出成功轨迹里的 progress actions，简单 recipe 流程、单步无恢复流程会跳过；包含 move/dig/place/combat 等可复用 workflow，或者验证了历史失败经验的成功 run，才会生成候选。候选生成后还会查重，是否晋升 promoted skill 取决于 auto_promote 或人工审核。
