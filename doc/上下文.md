Context Manager 不是“拼 prompt 的工具函数”，而是 控制模型每一步能看到什么证据、什么规则、什么历史、什么技能 的信息调度层。

它的输入不是用户一句话，而是一堆运行时状态：
  当前 observation
  任务 task_spec
  允许动作 allowed_actions
  上一轮 previous_step
  任务记忆 task_memory
  run 内压缩轨迹 run_context
  相关 Skill
  相关 Learning Candidate
  知识检索结果


输出是：
messages: 真正发给模型的上下文
audit_messages: 用于审计的上下文
prompt_sections: 结构化记录这次 prompt 由哪些部分组成
retrieved_skills: 本轮注入了哪些 Skill
retrieved_learning_candidates: 本轮注入了哪些失败经验
prompt_visible_actions: 本轮模型能看见哪些动作


System Message:
  第 1 层：稳定 System Prefix
    固定身份 + 行为规则 + harness contract + ActionDecision 输出格式

  第 2 层：任务 System Suffix
    当前任务目标 + 成功条件 + verifier + 公开任务配置

User Message:
  第 3 层：动态 Observation
    当前状态、上一步结果、任务进度、压缩轨迹、任务记忆、知识检索结果、Learning Candidate、Promoted Skill、Planner plan。

  第 4 层：previous_visual_snapshot
    可选图片证据，只有上一轮成功请求视觉快照才有

1. 稳定 System Prefix
这是最基础的行为规则。不是每轮根据世界状态变，而是作为模型的长期规则。
你是谁、你能做什么、你不能做什么、你必须怎么输出。

Base System Prompt
Minecraft Common Sense
Harness Contract

Base System Prompt 基础身份和行为规则。
你是一个运行在 harness 里的 Minecraft 任务求解 agent，每轮只能选择一个经过验证的 harness action 来推进任务。

Minecraft Common Sense 它主要体现在默认行为规则里，Minecraft 行动常识 + 防幻觉规则：
不要编造方块、物品、实体、坐标、配方、背包内容；
目标不清楚时，优先 scan、query_inventory、request_visual_snapshot；
配方、术语、Mineflayer 行为不清楚时，先用知识工具；
不要重复失败动作，除非有新证据。

Harness Contract 是最重要的。它告诉模型：
你能用哪些 action；
每个 action 的用途是什么；
知识工具怎么用；
什么时候可以 submit_for_evaluation；
返回 JSON 必须长什么样。

2. 任务 System Suffix
当前任务本身的稳定信息。

Task Objective
Task Board Spec
Active Subgoal Spec

Task Objective 就是任务目标。比如：收集 1 个 dirt、合成 wooden_pickaxe
代码里的 task_objective 包括：task_id、goal、verifier、success_criteria、completion_authority

Task Board Spec 任务配置里的其他公开元数据，它来自 task_spec，但会过滤掉一些不该给模型看的字段，比如 runtime、training、初始背包、scripted_actions 等。

3. 动态 Observation
这是每一步都会变的部分。当前看到了什么、之前发生了什么、有哪些证据/记忆/知识可用。

task_progress 是：当前观察能不能证明任务完成。
比如背包里已经有目标物品，就可能显示 goal_satisfied_by_current_observation；如果还没有，就是 goal_not_yet_satisfied。
state_summary 是：给模型读的一句话状态摘要。
它会把目标、当前进度、当前状态、上一步结果压成一段文本。
compact_evidence 是：结构化证据。
它比 state_summary 更细，包含当前状态、目标检查、上一轮动作压缩结果。模型写 evidence 时，应该引用这里面的东西。
task_memory / run_context 是：历史和记忆。
因为不可能把所有旧步骤无限塞给模型，所以 harness 会压缩旧轨迹、知识记录、技能记录、agent memory，再放进来。
resolved_terms / retrieved_docs 是：知识工具返回或预取的知识。
比如模型不知道 “log” 应该对应哪个 Minecraft ID，或者不知道某个 recipe，这里会放查到的结果。
retrieved_skills / retrieved_learning_candidates 是：可复用经验或技能候选。
比如以前学过“怎么采集 dirt”“怎么处理导航失败”，会作为候选提示模型，但它们不是强制命令。
task_plan 是：当前计划信息，如果有的话。
这比 system suffix 更动态，因为计划可能随着任务推进更新。

3. previous_visual_snapshot
如果上一轮拍了图，就把那张图作为本轮额外观察证据给模型看。

它不是每轮都有。只有上一轮 action 是：
{"type": "request_visual_snapshot"}
并且结果成功、图片文件存在、大小和格式合规，才会追加到 user message 后面。
它的作用是补文本 observation 的不足。比如文字状态里没有清楚描述面前地形、方块布局、实体位置，模型可以看图辅助判断。
它不是规则，也不是任务说明，所以不放 system。它是观察证据，所以放在 user 的文本之后。



三、Context Manager 具体做了什么
你可以按 7 个动作理解。

第 1 步：读取任务目标
从 task_spec 里拿：
task_id
goal
allowed_actions
knowledge_tags
verifier 信息
budget 信息

第 2 步：整理当前环境状态
构造成 state summary：

第 3 步：处理 previous_step
上一轮 observation
上一轮 action
上一轮 action_result
上一轮 verifier

第 4 步：压缩 run_context
完整轨迹会进数据库，但模型不能每轮看完整轨迹。
所以系统维护 RunContextMemory，里面有压缩后的运行内记忆：
trajectory ledger: 轨迹摘要
knowledge ledger: 本 run 查过哪些知识
skill ledger: 本 run 注入过哪些 skill
memory entries: 模型请求写入的任务记忆

第 5 步：按需知识检索,知识检索采用 agent-driven 的按需方式。Harness 负责只读边界、来源记录、长度预算和审计，而不是每轮把知识库全部注入 prompt。
知识工具包括：
resolve_terms
get_recipe
retrieve_docs

第 6 步：检索相关 Skill
去 Skill Library 找相关 promoted skill。
模型看到的是：
经验建议：采集方块后要确认掉落物进入背包。【这个技能大概怎么解决问题、可参数化的步骤、失败时怎么办】
参数化步骤：scan -> move -> dig -> scan drops -> move to drop -> wait -> query inventory。
恢复策略：如果 dig 成功但 inventory 未增加，优先找掉落物


第 7 步：检索 Learning Candidate
比如之前失败过：
挖了 oak_log，但没捡起来
当前又是采集类任务，那么 Context Manager 可以注入：
Known failure hypothesis:
After digging target block, inventory may not increase until dropped item is picked up.
Suggested recovery:
scan_dropped_items -> move_to drop -> wait_ticks -> query_inventory
这会提醒模型避坑。

你可以这样说：
Context Manager 负责管理模型每一步能看到的信息。我把上下文拆成三层：静态 System Prompt、稳定 Harness Contract 和动态任务状态。System Prompt 定义模型行为边界；Harness Contract 定义当前 action scope、工具参数和输出协议；动态上下文包含当前 observation、任务目标、压缩轨迹、任务记忆、知识查询结果、相关 Skill 和 Learning Candidate。完整轨迹始终写入数据库，但不会完整塞进模型窗口，而是通过 RunContextMemory 做分层压缩。Skill 也不是全量注入，而是根据 task scope、trigger、allowed actions 和当前状态检索少量相关经验，并以 strategy summary、parameterized plan、recovery policy 的形式注入。这样可以降低 prompt 膨胀和无关技能干扰，同时保证模型每一步都有足够证据做受约束决策。

最关键的一句：
Context Manager 的本质是信息治理：让模型看到“足够做对下一步”的信息，而不是看到“系统知道的一切”。


问题：
1. 检索相关 Skill
  Skill trigger 命中：权重最高
  task_scope 命中：次高
  当前允许动作和 skill action_plan 重合：加分
  dependency 命中：加分
  name / description / strategy / plan 里有关键词：少量加分

2. 如何确定skill召回的规则？"
Context Manager 每轮 build context 时，会先构造一个查询文本：
  1. query：Skill 召回是项目实现的确定性关键词检索，不是向量搜索。Context Manager 在每轮构建上下文时，会从任务目标、任务描述、当前 observation、解析出的 canonical id、允许动作和上一轮失败信息里构造查询，然后和 promoted skill"retrieval" 的 triggers、task_scope、dependencies、action_plan、strategy_summary、parameterized_plan、name、description 做匹配得到raw_score

  权重：trigger 命中 > task_scope 命中 > 当前允许动作和 skill 动作重合

  2. 第二层是 relevance，负责过滤：它更关注当前任务核心语义，比如 task_id、goal、description、verifier 目标和 canonical id，有多少被这个 skill 覆盖；如果命中当前失败点，比如 no_path，也会提高相关度。

  3. raw_score 看“匹配信号强不强”，relevance 看“是否真的适合当前任务”。最终先过滤掉 relevance 低于阈值的 skill，再按 relevance 降序、raw_score 降序选少量 skill 注入上下文。这样做的目的，是避免只因为两个技能都用了 move_to 这类通用动作就误召回，同时又能优先召回真正覆盖当前任务目标或失败恢复场景的技能。

3. 为什么不用向量检索 skill？
因为 skill 召回更需要精确匹配任务目标、动作范围和失败原因，比如 oak_log、no_path、dig_block_at。确定性关键词和权重更可解释，也方便审计；向量检索容易召回语义相近但动作不适用的技能。

4. 怎么压缩的：
轨迹压缩的原则是：完整 trace 持久化到数据库，模型上下文只保留决策需要的压缩证据。每个 action_result 会先被转换成 compact evidence，只保留动作类型、目标、成功状态、关键状态变化、背包变化和失败原因。

Context Manager 再做分层压缩：轨迹压缩是分档的。空间够时用 hierarchical：最近 2 步保留细节，旧历史按动作阶段合并成 segments；如果超预算，切到 aggressive：segments 进一步瘦身，最近步骤只保留 1 步；如果还超预算，就退化成 episode summary，把旧历史合并成整体摘要，只保留最近 1 步的高保真证据。这样能保证 prompt 不膨胀，同时下一步决策最依赖的最近状态不会丢。
够：
  segments:
    scan 阶段：扫描过 oak_log，找到几个候选
    move 阶段：第一个目标 no_path，第二个目标可达
  recent_steps:
    move_to 成功
    dig_block_at 成功，背包 +1 oak_log

合并：不再保留很多细节，只保留“过去发生过什么结论”和“最近一步的具体证据”。
  segments:
    scan/move 摘要：找到 oak_log；一个目标 no_path，后续换目标成功
  recent_steps:
    dig_block_at 成功，背包 +1 oak_log

狠：整个历史的一句话/几句话总摘要、最近 1 步
  episode_summary:
    已经扫描并尝试多个 oak_log，曾遇到 no_path，后续换目标成功并挖到 oak_log。
  recent_steps:
    dig_block_at 成功，背包 +1 oak_log

5. 预算：
同时，run_context 里还有知识、技能和记忆预算。知识查询结果是只读且可重复获取的，所以当上下文压力变大时，系统会优先减少 knowledge 的详细内容，只保留摘要或让模型之后重新查询；轨迹里的最近动作和当前失败证据优先保留。这样既避免 prompt 随任务变长无限膨胀，又保证模型下一步决策有足够证据。


6. SKILL
在 Skill 消费阶段，根据任务目标、动作范围、Skill Trigger、Task Scope、前置条件和依赖关系检索相关 Skill，再将其转换为紧凑的 strategy_summary、parameterized_plan 和 recovery_policy 注入上下文。Skill 采用按需加载方式，避免将整个技能库加入每轮 Prompt。

strategy_summary = 技能总体策略，用一句话告诉模型“怎么做”
parameterized_plan = 参数化步骤，不绑定旧 run 的固定坐标，而是告诉模型按当前环境替换目标
recovery_policy = 如果失败了，下一步怎么恢复


Skill 按需加载后不会把完整 SkillSpec 塞进 prompt。完整 skill 里有来源轨迹、验证信息、统计和审计字段，太长也容易干扰模型。Context Manager 只把召回到的 promoted skill 转成紧凑摘要，主要包括 strategy_summary、parameterized_plan 和 recovery_policy。strategy_summary 说明总体策略，parameterized_plan 保留可复用步骤但用当前 observation 替换具体目标，recovery_policy 提供失败恢复建议。这样模型能参考历史经验，但仍然需要基于当前环境一步步调用受控 action，而不是直接重放旧轨迹。

7. skill去重
Skill 去重分两层。第一层是数据库身份唯一性，name + version 不能重复；第二层是语义去重，比较新 candidate 和已有 skill 是否本质上做同一件事。它会比较动作类型、动作目标、触发词、任务范围、依赖项和名称，并按权重计算相似度，其中动作类型和动作目标权重最高。如果总相似度超过默认阈值 0.82，就认为这是重复技能，不再单独晋升。这样可以避免同一个采集流程因为名字不同被反复写入技能库。


8. skill 结构：
概念上，一个 Skill 可以分成四块。第一块是身份信息，比如 name 和 version，用来标识技能版本，并作为数据库唯一键；真正防止语义重复时，还会比较动作类型、目标和触发词等相似度(0.82)。
第二块是status用于启用/禁用/待审核
第三块是召回信息，包含任务类型、目标 ID、触发词和所需动作，用于和当前任务做相关性匹配。
第四块是使用与审计信息：strategy_summary、parameterized_plan 和 recovery_policy 会被压缩注入上下文
第五块provenance为该skill对应的run的信息，用于人工审计和来源追踪：source_run_id、source_step_range、source_evidence、verifier_stats、validation 和 metrics 用来追踪这个技能来自哪次 run、效果如何、是否可信。
